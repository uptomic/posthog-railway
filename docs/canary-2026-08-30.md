## Restore-rehearsal migration finding

The later restore rehearsal for locked candidate
`da93d8bbd71e23d49a8372ec43b4a4c7f75c1316` found that a direct jump from the inherited
pre-0210 ClickHouse ledger is unsafe. Current source causes historical replay migrations to refer to
columns introduced later in the same chain.

The release lock therefore includes two exact predecessor images. On the disposable restored
ClickHouse volume, Migration Bridge 1 and Migration Bridge 2 each completed successfully in order.
The final migrator then completed successfully with the locked latest-release image, leaving 315
entries in the ClickHouse migration ledger. The successful restore-migrator service was
`edffccec-84c9-4694-8bca-25680d59a6d6`, deployment
`a7a28a50-9dcf-4921-bfe5-0de411a37c33`. Bridge success alone is not the migration gate; the final
release migrator must also finish successfully.

The same candidate replaces the retired standalone Cyclotron janitor with the official Node image in
`cdp-cyclotron-v2-janitor` mode. Its isolated `cyclotron_node` database is migrated first with the
locked `sqlx-migrate` image and the explicit command
`/migrations/bin/migrate-entry cyclotron-node`. Set `CYCLOTRON_NODE_DATABASE_URL` on that one-shot
service; `DATABASE_URL` alone is ignored by this entrypoint. PersonHog Replica and Router are
required upstream of the Node modes. Replay also requires `recordings-blob-ingestion-v2` and
`recording-api`; replay capture and Kafka alone do not write the replay events table.

Feature Flags uses the same `SECRET_KEY` as Web. The service starts without it, but logs that
encrypted remote configuration cannot be decrypted, so that warning is a failed canary.

Web and Worker must have `RECORDING_API_URL` plus a matching `INTERNAL_API_SECRET`, and must enable
PersonHog with the Router address. The restored-data replay canary passed only after this complete
topology was present.
